## 4. Established Semantics

### 4.1 System Field Engineering Law

FIELD + RELATION + STATE + DELTA + BOUNDARY + AUTHORITY + RECONSTRUCTION

FIELD: resolved relational context in which coherent action can occur.

RELATION: meaningful connection between system elements.

STATE: current authoritative configuration.

DELTA: material change to state or relation.

BOUNDARY: point beyond which the current Field cannot legitimately derive the next relation.

AUTHORITY: source able to close what autonomy may not.

RECONSTRUCTION: after material change, the Field re-resolves from authoritative state.

### 4.2 Child Field Law

Child Fields inherit parent relations.

Child Fields may narrow contextual visibility where the parent relation permits it.

Child Fields may never silently expand or redefine parent relations.

Viewport, accessibility, reduced-motion and responsive constraints may transform presentation, geometry, interaction form, disclosure depth, density, motion and semantic-preserving order.

They may not silently remove legitimate capability, hide material authoritative relation, make a valid effect unreachable, remove required proof, change authority or change system meaning.

Responsive transformation changes representation.

It does not change system possibility.

Tree organizes scope.

Graph preserves coherence.

### 4.3 Frontend Law

Frontend projects system state.

Frontend does not create system truth.

Frontend may hold local presentation state.

Frontend may not hold local semantic authority.

### 4.4 Effect Law

Candidate != Effect.

Request != Commit.

Animation != State.

No semantic success before commit.

### 4.5 Human Question Law

Human Question Capture occurs while:

Session = QUESTION_GENERATION
and
Burst = ACTIVE HUMAN_ONLY

Closing question generation freezes the human set and transitions the Session to QUESTION_CAPTURE.

QUESTION_CAPTURE is the post-freeze state.

Do not relocate capture into QUESTION_CAPTURE.

Architect visibly distinct:

* active human field
* own question visibility
* participants
* controller
* frozen human artifact
* authors
* verification

### 4.6 Mock Law

Do not architect against mock system truth.

Use real NQIRY relations wherever they exist.

Mocks are allowed only when a real relation does not yet exist and the architecture cannot otherwise be exercised.

Every permitted mock must be:

* MOCK
* NON_PROOF
* ISOLATED
* REPLACEABLE BY A NAMED REAL RELATION

Existing F04 MockProvider ceilings remain exactly as declared.

### 4.7 Boundary Law

Boundary states are distinct:

* unavailable
* denied
* rejected
* not found
* unknown
* network failure
* indeterminate
* loading
* failed command

They may not collapse into one generic error.

Read failure must not use mutation language.

Failure must never imply a commit that never happened.

### 4.8 Symbiotic Surface Invariant

On desktop, every PRIMARY RELATIONAL SURFACE must visibly embody the Field architecture.

Where supported by the real relation graph, a primary surface must visibly express:

* Core
* relational topology
* semantic nodes
* relation paths
* Field depth
* living background
* proof depth
* state-bound motion or its semantically equivalent reduced-motion representation

Forms, cards, tables, lists, drawers and panels are subordinate interaction instruments.

They may support the Field.

They may not become the Field.

A technically correct surface that collapses back into conventional dashboard composition fails the architecture.

A primary relational surface must not be dominated by:

* card grids
* conventional admin panels
* CRUD tables
* stacked forms
* generic SaaS detail-page composition

when the relation graph supports a richer Field representation.

This rule does not prohibit:

* forms
* lists

when they are the clearest local instrument.

It prohibits them from becoming the PRIMARY ORGANIZING GRAMMAR of a relational Field.

The Challenge Field remains the primary architectural demonstration surface.

It must make the difference between:

The visual system is derived from the relation graph.

No visual distinction may silently imply a system distinction that does not exist.

### 11.1 Core

A Core is a semantic center of the active Field.

A Core may represent:

* Access when unauthenticated
* current Workspace
* current Challenge
* current Session
* active Human Question Field
* Frozen Question Artifact
* Governance root when governance is active focus
* Boundary state when no object can be safely projected

Core means:

* primary object of current coherent action
* highest local relational gravity
* main reconstruction anchor
* source from which visible child relations are resolved

Core does not mean:

* global importance
* permanent hierarchy
* authority by default
* ownership unless established
* centrality in backend graph unless projected

### 11.2 Orbit

An Orbit is a visible relation band around a Core.

Orbit may mean:

* contained relation
* dependent state
* participant relation
* session relation
* governance relation
* evidence relation
* possible next relation
* lifecycle-adjacent relation

Orbit must not be used when:

* relation is not established or explicitly meaningful
* circular placement would imply false hierarchy
* items are merely a list with no relational orbit
* viewport would destroy semantic order
* proof requires linear trace
* boundary state is more important than membership

Orbit transformation may never remove legitimate capability.

* workspace
* challenge
* session
* participant
* member
* role
* grant
* authority holder

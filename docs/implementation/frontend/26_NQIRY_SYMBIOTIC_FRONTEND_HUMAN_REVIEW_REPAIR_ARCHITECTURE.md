# 7. HARD WORKSPACE DEDUPLICATION LAW

THIS IS A HARD ACCEPTANCE BOUNDARY.

The current Workspace overview is NOT acceptable while one canonical Workspace can appear as repeated or duplicate-looking primary nodes.

Required invariant:

`ONE CANONICAL WORKSPACE ID -> ONE PRIMARY VISIBLE WORKSPACE NODE PER PROJECTION CONTEXT`

Canonical deduplication key:

`workspace.id`

Do not deduplicate by:

- display label
- route position
- array position
- object reference
- page section
- current index
- fetch batch
- textual equality alone

The visible projection MUST normalize the Workspace collection before geometry is calculated.

The geometry engine MUST consume normalized canonical Workspace identities.

The renderer MUST NOT independently render the same canonical Workspace in multiple stacks.

If the server returns repeated membership records that map to the same Workspace, normalize them before projection.

If the same Workspace appears through multiple valid relations, the UI may show multiple relation edges, but it must not create multiple indistinguishable primary Workspace bodies.

Hard law:

`MULTIPLE RELATIONS TO ONE WORKSPACE != MULTIPLE PRIMARY WORKSPACE NODES`

Allowed:

One Workspace node with multiple relation indicators.

Allowed:

One primary Workspace node plus an explicitly distinct preview or relation lens, if visibly and semantically different.

Forbidden:

Five nodes with the same Workspace name, same state, and same meaning.

Forbidden:

One left column of duplicates plus another right column of the same Workspace.

Forbidden:

Repeated Workspace nodes caused by repeated projection adapters.

Forbidden:

Layout code that duplicates visible nodes to fill geometry.

Acceptance question:

`Can a human reasonably believe the same Workspace exists multiple times?`

If yes, FAIL.

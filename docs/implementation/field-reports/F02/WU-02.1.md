## A structural discovery, caught before any test ran (disclosed, not hidden)
Before writing `create_challenge`, I read `commit/coordinator.py` and
`boundaries/bnd_014_commit.py` directly to check whether
`CommitCoordinator.commit()` — the mechanism every prior F01/F02
Command used — could support a Command with no `HumanAuthorityBinding`
requirement at all. It cannot, structurally:
`CommitCoordinator.commit()`'s `required_authority_class`,
`authority_scope_type`, `authority_scope_id` parameters are all
non-optional, and `Bnd014CommitEvaluator.evaluate()`
**unconditionally** calls `AuthorityResolver.resolve()` — there is no
code path that skips this. `AUTH-DEP-CH-001` requires no binding at
all (ROLE alone, 04 §84 "CLOSED. Facilitator has source authority.") —
there is no authority class this Command could correctly hand to
BND-014.

This is the same root shape `workspace_creation_handler.create_workspace`
already solved for a different reason (its own circularity: "the actor
does not yet hold the authority being checked"). `create_challenge`
mirrors that Command's hand-rolled `connection.begin_nested()` pattern,
adapted: unlike Workspace creation, `commands.workspace_id`'s FK is
already satisfiable here (the target Workspace already exists), so
`command_repository.record_attempt` happens normally, **outside/before**
the SAVEPOINT rather than inside it. A failure inside the SAVEPOINT is
caught and re-raised as `commit.coordinator.CommitFailedPrecommit` —
the same exception type a `CommitCoordinator`-based Command's caller
would see — and `record_outcome` is always called
(`FAILED_PRECOMMIT`/`COMMITTED`), matching every other governed
Command's observable behavior even though the internal mechanism
differs. `AuditEvent.authority_source_ref` (non-optional `uuid.UUID`)
is set to a fresh `uuid.uuid4()` when no real binding exists —
mirroring `CommitCoordinator`'s own internal fallback for the identical
case, not invented here.

This is the **third** time in this Field that "version the creation of
a new child row against its parent's own version, never against the
new row itself" has been the correct pattern (`AddMember` in F01,
`GrantHumanAuthorityBinding` in WU-02.0 — found there as a real bug —
and now `CreateChallenge`, applied correctly from the start because the
lesson was already known): `target_ref = workspace_target_ref(workspace_id)`,
`expected_versions={target_ref: workspace.record_version}`, freshness
re-checked immediately before the SAVEPOINT.

## Implementation

### `create_challenge` — precommit chain BND-001/002/003/004, no BND-005
The first Command in this codebase whose precommit chain omits BND-005
entirely — every prior governance-shaped Command
(`AddMember`/`RevokeHumanAuthorityBinding`/`GrantHumanAuthorityBinding`)
required BND-004 (role) **and** BND-005 (authority) together.
`AUTH-DEP-CH-001` names ROLE alone; `_CHALLENGE_CREATOR_ROLES = {FACILITATOR}`
is the only accepted role for BND-004. BND-004 is only evaluated when
`actor_membership is not None` — for a genuinely non-existent Workspace,
a separate BND-001/002-only precheck (mirroring
`AddMember`/`RevokeHumanAuthorityBinding`/`GrantHumanAuthorityBinding`'s
own established precheck for the `commands.workspace_id` FK hazard)
denies before `record_attempt` is ever called with a target that
cannot exist.

Empty/whitespace-only `title` is rejected with a plain `ValueError`
**before** `workspace_repository.get()` is even called — no boundary
evaluation, no `commands` row, no write. Mirrors
`create_workspace`'s own `workspace_name` validation precedent.

### `get_challenge` — the "Workspace scoped" (not "read authorized") read chain
`docs/architecture/14_IMPLEMENTATION_SEQUENCE.md` §13's own QUERY
REGISTRY names no standalone `GetChallenge` row at all. Its closest
siblings (`GetSession`, `GetBurst`, `GetAIAnalysis`) are all
"Workspace scoped" — BND-001/002/003 only, no `AuthorityResolver`
resolution — distinct from the stricter "Workspace scoped/read
authorized" group (`GetDecision`, `GetQuestionSelection`).
`get_challenge` mirrors the "Workspace scoped" group exactly, following
`session_view_query.get_session_view`'s own established implementation.
Existence is checked first (`challenge_repository.get()`); `None`
returns `ChallengeViewNotFound` immediately, before any boundary
evaluation — BND-002 needs the Challenge's own real, stored
`workspace_id` to resolve against, which cannot exist without the row.
The caller's own claimed `workspace_id` argument is never itself
authoritative — BND-002 always resolves against
`challenge.workspace_id` read fresh from the repository (proven by
`test_forged_workspace_in_request_is_ignored_the_real_challenge_workspace_governs`).

## Negative / adversarial tests
**Create:**
- The Workspace's own founder (Owner), alone in their own Workspace,
  cannot create a Challenge — `ChallengeCreationDenied`, zero rows
  (human-confirmed intentional, see WU-02.0's own recorded decision).
- A Contributor (non-Facilitator member) cannot create.
- A non-member actor cannot create.
- A genuinely non-existent Workspace denies (BND-001/002 precheck),
  zero `commands` rows.
- Non-human actor (parametrized SYSTEM_SERVICE/AI_PROCESSOR/EXTERNAL_SYSTEM)
  denied at BND-001.
- Empty/whitespace-only title rejected before any boundary evaluation
  or write, zero rows.
- Cross-Workspace: a real Facilitator in Workspace A cannot create in
  Workspace B, even though they hold a real Facilitator role somewhere.
- (Addendum) A retried call with the same `command_id` + `idempotency_key`
  returns the same `challenge_id`, and exactly one `challenges` row
  exists at the target Workspace — mandatory adversarial attack
  "committed duplicate" (14 §27), see Addendum above.

**Read:**
- Non-existent `challenge_id` → `ChallengeViewNotFound`, distinct from
  `ChallengeViewDenied` (no DENY reason for "no such object", mirrors
  `SessionViewNotFound`'s own precedent).
- A cross-Workspace stranger (real user, real different Workspace, not
  a member of the Challenge's own Workspace) → `ChallengeViewDenied`.
- Forged `workspace_id` attack: a real Facilitator of Workspace A
  claims a real, different Workspace B (not their own, not the
  Challenge's own real Workspace) while asking to read a Challenge
  that actually belongs to Workspace A → `ChallengeViewDenied` (BND-002
  resolves against the Challenge's own stored `workspace_id`, never the
  caller's claim).
- Non-human actor (parametrized) → `ChallengeViewDenied`.

## Addendum (2026-09-22): idempotent retry closed, not deferred
This report originally disclosed `idempotency_key` as accepted but not
enforced by `create_challenge`'s hand-rolled path, deferred pending a
real frontend double-submit case. Human operator reviewed and rejected
the deferral: build it now, before "Challenge semantic projection."

**Fix**: `create_challenge` now takes a required `idempotency_port:
IdempotencyPort` parameter. After the precommit chain ALLOWs, it calls
`idempotency_port.begin(envelope, seen_at=occurred_at)` — the identical
call `AddMember`/`RevokeHumanAuthorityBinding`/`GrantHumanAuthorityBinding`
already make at the same point in their own pipelines. On success (the
new attempt is a legitimate `PROCEED_NEW`/`PROCEED_FRESH_ATTEMPT_AFTER_FAILED_PRECOMMIT`),
the write proceeds through the SAVEPOINT exactly as before, and
`idempotency_port.mark_committed(..., result_ref=str(challenge_id.value))`
is now called inside that SAVEPOINT once the write succeeds (a failure
inside the SAVEPOINT now also calls `idempotency_port.mark_failed_precommit(...)`,
so a genuinely failed attempt never leaves its own idempotency record
stuck IN_PROGRESS, blocking every future retry).

Unlike every `CommitCoordinator`-based Command in this codebase — which
sets `result_ref = str(commit_id.value)` and simply lets
`IdempotencyAlreadyCommitted` propagate uncaught to their own caller,
leaving "materialize the prior result" to a not-yet-built HTTP layer —
`create_challenge` sets `result_ref = str(challenge_id.value)` and
catches `IdempotencyAlreadyCommitted` itself: it loads the real,
already-created Challenge via `challenge_repository.get()` and returns
the identical `CreateChallengeResult` shape a fresh call would, true
idempotent replay rather than an exception carrying a hint. This is a
deliberate, disclosed divergence from `AddMember`'s own established
propagate-only pattern, made because this Work Unit's own explicit
requirement was literally "return the existing Challenge," not "signal
that one exists." Every other `IdempotencyLifecycleError`
(`IdempotencyInProgress`, `IdempotencyPayloadCollision`,
`IdempotencyIndeterminateBlocked`) still propagates uncaught,
unchanged — 14 §27 reserves "return the result" for
`RETURN_COMMITTED_RESULT` alone.

**Test written first, genuine RED confirmed, then reverted back to
RED for real proof (not skipped)**: `test_a_retried_call_with_the_same_idempotency_key_returns_the_same_challenge`
(`tests/e2e/test_create_challenge.py`) was written against the ALREADY-FIXED
implementation, so to honor genuine RED→GREEN rather than assert it
after the fact, the fix itself was temporarily reverted (the
`idempotency_port.begin()`/`mark_committed`/`mark_failed_precommit`
calls removed) and the test re-run — confirmed genuine failure: two
independent `ChallengeId` values, `assert second.challenge_id ==
first.challenge_id` failed for real
(`acfedccf-9b01-4e7f-803c-05347e1b792b` != `e596f779-08e4-4fe5-a44f-d68b0a85ea56`).
The fix was then restored and the same test re-run: **1 passed**. A
genuine retry reuses both the same `command_id` (09 §4.3: a different
`command_id` is a different logical operation by definition, never a
retry) and the same `idempotency_key`, with a fresh `attempt_id` per
physical call — exactly what `command_repository.record_attempt`
already expects for a legitimate retry (a repeated `command_id` with
an unchanged payload fingerprint records a new `command_attempts` row
only, never a second `commands` row).

## Why `CommitCoordinator` is used here, unlike `CreateChallenge`
AUTH-DEP-CH-001 (WU-02.1) names no `HumanAuthorityBinding` at all —
`CreateChallenge` hand-rolls its own atomic write because there is
structurally no `AuthorityClass` to hand `CommitCoordinator`.
AUTH-DEP-SESS-001 is the opposite case: a real, checkable authority
(`SESSION_CONTROL_RIGHT`, scope `CHALLENGE:challenge_id`) — so
`CommitCoordinator` is both usable and required. `create_session`
mirrors `application.human_decision_handler.open_decision_consideration`'s
own shape directly (a new child object, gated by a real
`HumanAuthorityBinding` scoped to its parent Challenge), not
`CreateChallenge`'s.

## A resolved design question, textually grounded (not guessed, not asked)
Whether `create_session`'s own precommit chain should include BND-007
(state-transition legality) was genuinely unclear from precedent
alone: `OpenDecisionConsideration` (the closest sibling shape) DOES
run BND-007 even for its own "absent -> first state" transition. But
`domain.session_transitions`'s own `TransitionSpec` for TRN-SESS-001 —
03 §15's own per-transition dependency list, transcribed verbatim —
gives `required_boundary_dependencies = (IDENTITY, WORKSPACE,
AUTHORITY, AUDIT)`, DELIBERATELY omitting `STATE_TRANSITION` (which
TRN-SESS-002, "Begin Setup", the very next transition, explicitly
includes). `domain.decision` exposes no equivalent explicit
per-transition list to draw this same distinction from, so
`OpenDecisionConsideration`'s own chain shape is not directly
comparable evidence here. Read literally, 03's own text is more
specific and more directly on-point than a same-shaped sibling's own
implementation choice — `create_session`'s own precommit chain
therefore omits BND-007: `(BND-001, BND-002, BND-003, BND-004,
BND-005)`. This did not rise to a stop-and-ask: the domain module's own
`required_boundary_dependencies` field is a first-class, directly
readable textual source, not an inference from silence.

Genuine RED. Restored, then run again: **8 passed, 2 failed** — a real
defect, this time in the TEST FIXTURE itself (not the implementation):
```
CommitDenied: STALE_VERSION:challenge:<uuid>
```
`_create_session`'s own test helper passed
`current_version_reader=SqlAlchemyWorkspaceVersionReader(...)`, but
`create_session`'s own `target_refs`/`expected_versions` key on the
CHALLENGE's own ref (`challenge_target_ref`, the established "version
against the parent" pattern — the fourth occurrence of this exact
pattern in this Field). A `WorkspaceVersionReader` cannot answer for a
Challenge target ref, so `current_versions[challenge_ref]` read `None`
against `expected_versions[challenge_ref] = 1` — a genuine, caught
STALE_VERSION mismatch. Fixed by using
`SqlAlchemyChallengeVersionReader(db_connection, challenge_id=challenge_id)`
instead, the same reader `human_decision_handler`'s own test file
already establishes for the identical shape (verified directly against
that file before making the fix, not guessed). Re-run: **11 passed**
(the 11th, `test_a_created_session_is_readable_through_get_session_view`,
was added after this fix — a genuine cross-Work-Unit composition
proof, not part of the original RED count).

## Known limitations
- No HTTP route yet — backend-only, matching every other F02
  Command/Query/projection built so far; "legal state-transition API"
  and "inquiry-position frontend" are later in 19 §22's own sequence.
- `applied_method_key`/`applied_method_version` are accepted as plain,
  caller-supplied values with no catalog validation — no InquiryMethod
  registry exists anywhere in this codebase yet (verified directly,
  not assumed absent); 12 §9 itself calls this "CONFIGURATION" with no
  further validation mandate at this build phase. Matches
  `create_workspace`'s/`create_challenge`'s own equally minimal
  free-text field validation.
- Idempotent-retry-returns-existing-result semantics (the WU-02.1
  addendum's own pattern for `create_challenge`) were NOT built here —
  `create_session` uses `CommitCoordinator` directly, whose own
  established behavior (`AddMember`/`GrantHumanAuthorityBinding`/
  `OpenDecisionConsideration`) is to let `IdempotencyAlreadyCommitted`
  propagate uncaught rather than materialize the prior result itself.
  `create_challenge`'s own divergence (catching it and returning the
  prior Challenge directly) was a deliberate, human-requested
  exception for that Command specifically, not a new default this
  codebase now expects of every Command — `create_session` follows the
  more common, already-established `CommitCoordinator` convention
  instead, not a silently reduced standard.

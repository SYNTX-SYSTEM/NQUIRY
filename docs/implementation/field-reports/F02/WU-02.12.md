## FBR-B — idempotency / command identity

**Symptom.** The bootstrap reading was: "same key, different payload on a
Session Command → `committed` + `replayed`."

**Tracing upstream found two broken relations, not one:**
1. `application.session_control_handler._replay_guard` decided the replay
   with its own rule, `existing.command_id == ident.command_id`. Because the
   HTTP transport uses the key *as* the command id, that comparison is
   always true. It never consulted the authoritative disposition
   `commit.idempotency.decide_idempotency_action` (14 §27), which compares
   the payload fingerprint. A key committed for Session S1 was replayed
   against S2, and a key committed with `expectedVersion: 1` was replayed
   for `expectedVersion: 2`.
2. **The first broken relation is deeper**, at
   `persistence.command_repository.record_attempt`, the home of command
   identity (09 §4.3: `command_id` is "the stable identity of one logical
   requested consequential operation"). It compared Workspace and payload
   fingerprint but **not the Command type**. `CMD_PREPARE_BURST` and
   `CMD_OPEN_QUESTION_GENERATION` share a payload shape (session id +
   expected version), so their fingerprints are equal. RED proved that
   reusing a prepare-burst key for open-question-generation **committed the
   QUESTION_GENERATION effect under a `commands` row that says
   `CMD_PREPARE_BURST`**. That is provenance corruption at the effect gate's
   input.
3. **Side relation.** A key reused across Workspaces raised
   `CommandWorkspaceMismatch`. `http_f02` did not map it, so the API
   answered **HTTP 500**.

**Authoritative homes.** Command identity lives in
`persistence/command_repository.py`. The idempotency disposition lives in
`commit/idempotency.py` and is reused, not duplicated. The transport mapping
lives in `application/http_f02.py`.

**Test intent.**
- MUST BECOME TRUE: an identical retry is replayed without a second effect;
  any other reuse is `rejected` (`IDEMPOTENCY_KEY_REUSED_FOR_DIFFERENT_COMMAND`).
- MUST REMAIN IMPOSSIBLE: a changed payload reported as a replay; an effect
  on another Session; one command id carrying two Command types; a 500 on
  cross-Workspace reuse.
- FALSIFIER: `tests/e2e/test_wu_02_12_closure.py` (FBR-B cases) and
  `tests/command_commit_event/test_command_repository.py::test_denies_reusing_a_command_id_for_a_different_command_type`.

**RED evidence.** Captured before any repair: `test_wu_02_12_closure.py`
had **11 failed, 1 passed**. The passing test is the positive control
(identical retry).
- Changed payload: 200 `committed` (expected 400 `rejected`).
- Other Session: `committed`/`replayed`.
- Cross-type: `{kind: committed, replayed: False}`, meaning the effect was
  really committed.
- Cross-Workspace: 500 Internal Server Error.
- L1: the command-repository test failed at collection
  (`CommandTypeMismatch` did not exist).
- L7 real stack, against the pre-repair containers: the changed-payload
  reuse returned HTTP **200**.

**Root repair.**
- `command_repository.record_attempt` raises the new `CommandTypeMismatch`
  when an existing `command_id` was recorded under another Command type.
- `_replay_guard(…, payload)` now computes the real payload fingerprint and
  applies `decide_idempotency_action`:
  - COMMITTED + same fingerprint → `IdempotentReplay`;
  - FAILED_PRECOMMIT → proceed (14 §27 fresh attempt);
  - collision → `IdempotencyPayloadCollision`;
  - IN_PROGRESS / INDETERMINATE → their existing exceptions.

  The four Session Commands build their payload once, before the guard, and
  pass the same object to the envelope. The guard and the envelope therefore
  fingerprint the same value.
- `http_f02._command_outcome` maps `CommandTypeMismatch` and
  `CommandWorkspaceMismatch`, alongside the existing collisions, to
  `rejected`.

**Forward propagation.**
- Challenge, Session and grant creation already relied on
  `IdempotencyPayloadCollision` / `CommandPayloadConflict`. They now also
  get the type and Workspace checks.
- F01 / PKG routes do not take client keys (server-generated
  `uuid4` command ids), so they are unaffected.
- No schema change: `commands.command_type` already existed.

**GREEN.** `test_wu_02_12_closure.py` passes 12/12. Command repository
passes 11/11. L7: `wu-02-12-closure.real.spec.ts` passes on desktop and
mobile.

## FBR-C — outcome vocabulary on the wire and in the UI

**Symptom.** `/workspaces/{w}/sessions/{s}/decision` with a malformed id
shows "Unable to load this Session.", a network-error banner, for a server
verdict.

**First broken relation.** Producer ↔ consumer vocabulary. F02 WU-02.9 (E9)
changed two producers to emit `rejected`:
- `GET /workspaces/{w}/sessions/{s}` → consumer `client.ts
  parseSessionReadResult`;
- `GET /workspaces/{w}` → consumer `workspaceClient
  parseWorkspaceOrientationResult`.

Neither consumer was updated, so both threw. That is the same relation class
F02's DeepSweep claimed to have covered. The sweep found two further members
of the class:
1. **Framework validation.** A body that fails the route's pydantic model
   returned FastAPI's bare `{"detail": …}` with status 422. That collides
   with the envelope's `blocked` (422), is not `rejected`, and no consumer
   parses it.
2. **Collapsed outcome.** `http_dispatch` folded a proven SAVEPOINT rollback
   (`CommitFailedPrecommit`) into
   `{"kind":"rejected","reasonCode":"FAILED_PRECOMMIT:…"}` on decide,
   add-member and revoke. That merges two of the four generic outcomes
   (03 §8, 10 §4: "does not add a fifth", and does not merge two either).

**Authoritative homes.**
- The API adapter (`apps/api/src/nquiry_api/main.py`), where framework
  validation happens.
- `application/http_dispatch.py`, the F01/PKG outcome mapping.
- Each consumer parser in `apps/web/lib/api/`.
- Each rendering consumer: `SessionViewContainer`, `DecisionSection`,
  `/login`, and the Workspace page.

**Test intent.**
- MUST BECOME TRUE: every emitted kind is parsed as itself and rendered as a
  verdict.
- MUST REMAIN IMPOSSIBLE: a verdict shown as a network error; a malformed
  login shown as "Incorrect email or password" (a false credential denial);
  an unknown kind defaulting to success.
- FALSIFIERS:
  - `test_wu_02_12_closure.py` (6 validation cases + failed_precommit);
  - `apps/web/tests/lib/outcomeVocabulary.test.ts` (7);
  - the real-stack WU-02.12 spec;
  - 2 mocked component-contract tests.

**RED evidence.**

  the fail-closed control.
- **Deviation, disclosed.** The backend failed_precommit test first failed

**Root repair.**

**Forward propagation.**

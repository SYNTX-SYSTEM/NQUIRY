## A second, resolved architectural question (disclosed, not silently decided)
While reconstructing F02's own baseline, `AUTH-DEP-CH-001` (Challenge
creation) was found to gate strictly on **Facilitator ROLE**, not a
binding — and the schema enforces exactly one role per person per
Workspace, meaning a Workspace's own founder (always `Owner`, never
simultaneously `Facilitator`) can structurally never create a
Challenge in their own Workspace under a literal reading. Presented to
the human operator with three options before writing any
`CreateChallenge` code (not yet built — that is WU-02.1's own scope,
not this Work Unit's); **confirmed decision: implement exactly as
specified** (`AUTH-DEP-CH-001`/19 §84, "CLOSED. Facilitator has source
authority.", "No implicit Owner/Facilitator substitution" — repeated
verbatim across 04/05) — a deliberate governance/facilitation
separation, not a bug. Recorded here because it directly shapes how
`WU-02.0`'s own `grant_human_authority_binding` will need to be used in
practice (the founder must grant a second, real member the Facilitator
role via `AddMember`, and that member creates Challenges — no

## Implementation

### The one real defect found: wrong optimistic-concurrency target for a Command that creates a NEW row
First implementation attempt modeled `grant_human_authority_binding`'s
own `CommandEnvelope.target_refs`/`expected_versions` against the
BRAND-NEW binding it was about to create (`authority_binding_target_ref(binding_id)`,
`expected_versions={target_ref: RecordVersion.initial()}`) —
mirroring `RevokeHumanAuthorityBinding`'s own shape, which is WRONG
for this Command: `revoke()` mutates an EXISTING row (versioning
against that row is correct), but `grant()` creates a NEW row with no
prior state at all. `CommitCoordinator`'s own BND-014 evaluator
compared `expected_versions[ref] = RecordVersion.initial()` (value 1)
against `current_versions[ref] = None` (the real
`SqlAlchemyAuthorityBindingVersionReader.read()` result for a
genuinely non-existent row) and correctly raised
`CommitDenied: STALE_VERSION` for every real commit attempt — 4 tests
failed with this exact error.

**Root cause, once traced**: `AddMember` (WU-01.5) already solved this
identical problem correctly — it also creates brand-new rows
(membership, role assignment) under an ALREADY-EXISTING Workspace, and
versions its own optimistic-concurrency check against the WORKSPACE
itself (`workspace_target_ref(workspace_id)`,
`expected_versions={target_ref: workspace.record_version}`), never
against the new rows it creates. `grant_human_authority_binding` needed
the identical fix: **the optimistic-concurrency target is the
Workspace, not the new binding** — the new binding has no prior state
to protect against staleness; what matters is that the Workspace
itself did not change between authority resolution and commit.
**Fixed**: `target_ref = workspace_target_ref(workspace_id)`,
`expected_versions={target_ref: workspace.record_version}`,
`current_version_reader` is now an injected parameter (matching every
other Command's own convention) rather than a hardcoded, one-off
`_GrantVersionReader` class this Work Unit's own first draft
mistakenly introduced (removed — `SqlAlchemyWorkspaceVersionReader` is
the correct, already-existing reader, same one `AddMember` already
uses).

### Design decisions
- **`GovernanceRightNotGrantableViaGenericGrant`, raised before any
  boundary evaluation**: mirrors `OwnerRoleNotAssignable`
  (WU-01.5)/`GovernanceRootOrphaningRefused` (WU-01.6) exactly — the
  identical GAP-05-001 (Workspace root succession) refusal, from the
  third possible direction (grant, after refuse-to-grant-a-second and
  refuse-to-revoke-the-only-one). All three guards together make
  `WORKSPACE_GOVERNANCE_RIGHT` structurally immutable after founding,
  by design, not by omission.
- **BND-004 `accepted_roles={Owner}` / BND-005
  `required_authority_class=WORKSPACE_GOVERNANCE_RIGHT, scope_type="WORKSPACE"`**:
  identical gate to every other governance-write Command in this
  Field — only the Workspace's own governance root may grant new
  authority.
- **`scope_type`/`scope_id` accepted as plain caller-supplied
  values, not validated per-class**: mirrors `AuthorityBindingRepository.grant()`'s
  own existing, deliberately generic (non-authority-resolving) shape —
  this Command performs no scope-shape validation of its own beyond
  what the real DB trigger (`trg_habb_check_grant_preconditions`,
  GOV-002) already enforces for `WORKSPACE_GOVERNANCE_RIGHT`
  specifically (refused here anyway, before reaching that trigger).
  Each future Work Unit granting a SPECIFIC class (e.g. WU-02.x
  granting `SESSION_CONTROL_RIGHT` scoped to a real Challenge) is
  responsible for supplying the semantically correct scope — this
  Command does not invent per-class scope enforcement that 04/05 never
  specified.
- **Granting the same (user, class, scope) twice creates two
  independent rows**: not a defect, a disclosed, pre-existing
  data-integrity property (`AuthorityResolver`'s own
  `UNRESOLVED_AMBIGUOUS_ACTIVE_BINDINGS` verdict already exists
  specifically to handle this fail-closed) — this Command does not
  invent a new uniqueness constraint `grant()`/the schema itself never
  had.

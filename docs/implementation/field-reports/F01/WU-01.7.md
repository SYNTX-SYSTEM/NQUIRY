## Implementation

### Why this is a pure projection, not a new authority mechanism
`project_capabilities` reads
`AuthorityBindingRepository.list_current_bindings` directly rather
than calling `authority.resolver.AuthorityResolver.resolve()` once per
candidate `AuthorityClass`. This is deliberate and disclosed in the
module's own docstring: `list_current_bindings`'s own module docstring
warns it does not itself cross-check membership effectiveness (05
AC-05-004) — but this function's one required input, a genuine
`WorkspaceContext`, has ALREADY proven ACTIVE membership before
`project_capabilities` is ever called (`resolve_workspace_context`,
WU-01.3, cannot be constructed otherwise — its own `__post_init__`
enforces this at runtime). The effectiveness gap that warning
describes is closed by construction at the call site, not bypassed.
Re-implementing `AuthorityResolver`'s own resolution algorithm here
instead would have been the actual non-collapse violation (14 §16:
authority resolution is that module's one job).

### Why "non-proof demo state" (19 §21's fifth rendering category) is explicitly out of scope
No schema column or repository fact anywhere in this codebase marks a
`workspaces` row as fixture-sourced versus legitimately founded (F01
WU-01.4's own Option A resolution makes every NEW Workspace legitimate
by construction; a `NonProofWorkspaceBootstrap`-seeded demo Workspace
is distinguishable only by HOW it was created — a fact this repository
does not persist anywhere). Inventing such a marker now, with no
textual mandate from 19 or any earlier architecture document, would be
exactly the kind of undirected new capability 19 §2/§4 forbid.
Disclosed as a real, known gap for whoever builds the demo/production
distinction a later Field may need — not silently faked with a
placeholder `False`.

### Why `role` is exposed but never substituted for a capability
`19 §21 BACKEND REQUIREMENTS`: "No: ... role = right" — the identical
non-collapse rule `membership_operations_handler.add_member` already
established for the write side (WU-01.5). `CapabilityProjection.role`
is informational (frontend display: "you are a Facilitator here"), and
`governance_capable`/`authorized` are always computed from the real
`HumanAuthorityBinding` facts alone, never from `role`. The cross-
Work-Unit test (`test_revoking_the_only_binding_flips_authorized_back_to_false`)
proves this explicitly: revoking a Contributor's only authority
binding flips `authorized` to `False` while `role` stays
`CONTRIBUTOR`, unchanged and unrelated.

## Negative / adversarial tests
This Work Unit's own scope is a pure Query with no boundary chain of
its own to attack (identity/membership are proven upstream by
`WorkspaceContext`, reused not re-checked) — its adversarial coverage
is therefore correctness-under-state-combination, not authority
denial:
- A plain member with zero authority bindings: `authorized=False`,
  `governance_capable=False`, `held_authority_classes=frozenset()`
  (not an error, not a denial — a legitimate empty state).
- A member holding a non-governance binding (`DECISION_RIGHT`):
  `authorized=True`, `governance_capable=False` — proves the two
  booleans are independently computed, never conflated.
- A member holding multiple distinct binding classes: both appear in
  `held_authority_classes`, `governance_capable` still strictly gated
  on `WORKSPACE_GOVERNANCE_RIGHT`'s own presence.
- Cross-Work-Unit proof: revoking (WU-01.6) a member's only binding
  flips `authorized` back to `False` in the very next projection call
  — proves the "no caching, always fresh" discipline
  `AuthorityResolver`'s own module docstring establishes for
  `resolve()` extends transitively to this projection, since it reads
  the same live repository on every call.

  Work Unit does not attempt.

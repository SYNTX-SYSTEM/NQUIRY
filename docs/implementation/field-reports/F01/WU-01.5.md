"invite/add member" operation specifically — 04's own gap text: "AC-04-001

## Implementation

### The one real defect found: `commands.workspace_id`'s FK denies record_attempt for a genuinely non-existent Workspace, codebase-wide, not just here
WU-01.4b already discovered `commands.workspace_id`'s FK blocking a
target that does not exist YET (`CreateWorkspace`'s own founding
target). Writing this Work Unit's own adversarial test for "caller
supplies a `workspace_id` that never resolves to any real row at all"
surfaced the SAME constraint from the opposite direction: calling
`command_repository.record_attempt()` for such an ID raises a raw
`psycopg2.errors.ForeignKeyViolation` before `BND-002` ever gets a
chance to translate "Workspace not found" into a graceful `DENY`.

Neither `application.human_decision_handler` nor
`application.question_selection_handler` — the two existing full-chain
governed Commands this Work Unit's own pattern otherwise mirrors
exactly — has ever had this path exercised by a test; both call
`record_attempt` unconditionally before their own boundary chain, and
no existing test anywhere in this codebase supplies a genuinely
non-existent `workspace_id` to either. This is disclosed as a real,
pre-existing latent gap in the shared architecture, not something this
Work Unit invented.

**Fix applied, scoped to this Command only**: `add_member` now checks
`workspace_repository.get(workspace_id)` and, if `None`, evaluates
BND-001/002 alone (via the same registry, no separate machinery) and
raises `AddMemberDenied` immediately — before building the
`CommandEnvelope` or calling `record_attempt` at all. No `commands`
row is ever attempted for a Workspace that was never real. The other
two files were deliberately NOT modified (outside this Work Unit's own
scope; see "First Broken Relation" below for the disclosure that
belongs to the whole codebase, not just this file).

### Design decisions, each grounded in already-closed architecture
- **Accepted roles restricted to `{Facilitator, Contributor}`,
  `Owner` explicitly refused** (`OwnerRoleNotAssignable`, raised before
  any boundary evaluation): assigning the `Owner` role label without
  the matching `WORKSPACE_GOVERNANCE_RIGHT` binding would be a
  role/right collapse (19 §21: "No: role = right"); granting a SECOND
  `WORKSPACE_GOVERNANCE_RIGHT` binding for the same Workspace is 05's
  own `GAP-05-001` ("Workspace Root Creation and Succession...
  owner transfer and succession remain undefined"), `[UNDERDEFINED]` —
  refused outright rather than invented.
- **BND-004 `accepted_roles={Owner}`**: only the Workspace's own
  governance root may administer membership (05's exact closure text).
- **BND-005 `required_authority_class=WORKSPACE_GOVERNANCE_RIGHT,
  scope_type="WORKSPACE"`**: matches exactly how `CreateWorkspace`
  granted the founder's own binding (WU-01.4b) — the same scope
  triple, re-checked fresh by `AuthorityResolver` on every call.
  Cross-checked at both BND-004 (role) and BND-005 (right), never one
  substituted for the other (04/06 non-collapse).
- **Two writes (`create_membership` + `assign_role`) in one
  `MutationExecutor.apply()`**: AC-09-006's own governance-atomicity
  closure ("governance mutation bundles ... commit completely, or
  [are] treated as INDETERMINATE") is satisfied by construction — both
  calls share the one SAVEPOINT `CommitCoordinator._commit_inner`
  already opens; no extra code was needed to make this true.
- **Real DB constraints as the second line of defense**: adding an
  already-ACTIVE member hits `uq_workspace_memberships_active_pair`
  (a partial unique index this migration already defines); adding a
  non-existent user hits `fk_workspace_memberships_user`. Both
  propagate through `CommitCoordinator`'s own generic rollback handling
  as `CommitFailedPrecommit` — no new validation code was written for
  either, matching this codebase's established "checked at two
  independent layers" discipline.
- **`remove member`/`assign role` (post-creation)/`change role`/
  `revoke role`** (GAP-04-014's remaining four operations): real,
  equally-closed-by-05 scope, deliberately NOT built here —
  `SUCCESSOR_NOT_BUILT`, disclosed rather than rushed, to keep this
  Work Unit reviewable as one coherent Command.

## First Broken Relation
"A governed Command's `record_attempt` call can always run
unconditionally before its own boundary chain" — true for every
existing full-chain Command's own test suite (because none of them was
ever tested against a `workspace_id` that does not exist at all),
false in general, because `commands.workspace_id`'s FK makes the
Workspace's existence a genuine precondition of recording ANY attempt
against it — regardless of which Command. Fixed locally in
`add_member`; **not** fixed in `human_decision_handler`/
`question_selection_handler`, which remain exposed to the identical
unhandled `ForeignKeyViolation` for a forged/non-existent
`workspace_id`, disclosed here as a real, pre-existing gap in the
shared architecture rather than silently patched in files outside this
Work Unit's own scope. Flagging for whoever owns those two packages'
own future maintenance, or for a dedicated later Work Unit.

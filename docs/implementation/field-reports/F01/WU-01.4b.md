## Implementation

### Defect 1 — `expected_versions` for a target that does not exist yet
`CommandEnvelope.__post_init__` requires `expected_versions` to name
exactly `target_refs` (AC-09-001, a freshness predicate for every
mutation target). `workspace_id` is generated fresh inside this
Command and cannot have a "current" version. Fixed by following the
exact precedent already established in
`application.question_selection_handler._build_envelope` (its own
comment: "When the Session was not found, there is no real version to
name as 'expected'... `RecordVersion.initial()` is used only so the
envelope itself remains well-formed") — `RecordVersion.initial()`
names the version this Command's own write will give the row.

### Defect 2 — raw dict payload
`CommandEnvelope.__post_init__` rejects any `Mapping` payload (09 §9:
"raw dictionaries are rejected at public consequential boundaries").
Fixed by adding `CreateWorkspacePayload` (a one-field frozen
dataclass), mirroring `question_selection_handler.SelectQuestionPayload`'s
own precedent for a package-local payload contract.

### Defect 3 — `commands.workspace_id` FK cannot be satisfied before the Workspace exists (the real finding of this Work Unit)
Every other governed Command in this codebase calls
`command_repository.record_attempt()` BEFORE its mutation runs, so a
`commands` row survives even a subsequently failed attempt — a
genuine "this was tried" audit trail regardless of outcome. That
ordering is structurally impossible for `CreateWorkspace`:
`commands.workspace_id` carries a real, non-deferrable foreign key
(`fk_commands_workspace`) to `workspaces.id`, and the Workspace it
would reference does not exist until this Command's own write creates
it. Writing `commands` first violates the FK; writing `workspaces`
first as a separate, earlier transaction breaks atomicity (a founder
row could exist with no matching audit trail, or vice versa, if the
process died in between).

Fixed by bringing `workspaces` into existence FIRST inside the single
`connection.begin_nested()` SAVEPOINT, then calling `record_attempt`
against the now-real row, then the remaining domain rows, all in the
same atomic unit. This is disclosed honestly, not silently patched: a
FAILED founding attempt now leaves **no** `commands`/`command_attempts`
row at all — not even a `FAILED_PRECOMMIT` one — because the SAVEPOINT
rolls back the `commands` row along with everything else, and there is
no legitimate way to keep an operational record pointing at a
canonical record that was never actually brought into being. The
exception still propagates uncaught to the caller; nothing is
swallowed. See the module's own docstring
(`packages/application/workspace_creation_handler.py`, "WHY
`command_repository.record_attempt` RUNS *INSIDE* THE SAVEPOINT HERE")
and `test_mid_transaction_failure_rolls_back_every_row_including_the_attempt_itself`
for the proof.

### Defect 4 — `sqlalchemy` imported directly inside `application`
`scripts/check_architecture_dependencies.py` correctly flagged the
first draft: `packages/application` may not import `sqlalchemy`
directly (14 §3.1/§4). The first draft wrote `workspaces`/
`workspace_memberships`/`role_assignments`/`human_authority_bindings`
rows by hand with `sa.insert(...)`, exactly the pattern
`application.recovery_handler`'s own precedent (PKG-24) avoids by
delegating the actual write to a `persistence`-layer repository method
and only using the raw `connection` for `.begin_nested()`.

Fixed by adding the three repository write methods listed in "Files
changed" above and calling them instead. Each of the three
repositories' own docstrings already anticipated this exact moment
("governed mutation plan... until [HARD-DEP-001] is resolved" /
"no Command/CommitUnit exists yet for the write half") — this Work
Unit is that governed mutation plan materializing, not new,
undocumented architecture. `connection: Any` (not `sa.Connection`) in
the handler's own signature mirrors `recovery_handler.py`'s identical
workaround for the same layering rule.

### Why this Command does not call `CommitCoordinator`
Unchanged from the design recorded in WU-01.4.md: `CommitCoordinator.commit()`
hard-requires the actor to already hold `required_authority_class`
before the mutation runs — circular for a founding act, since the
`WORKSPACE_GOVERNANCE_RIGHT` binding is this Command's own output, not
its precondition. This Command performs its own governed write
instead, following `application.recovery_handler`'s disclosed
precedent (PKG-24) for the identical structural reason. Full reasoning
is in the module's own docstring.

## First Broken Relation
The relation that broke first, in the literal, useful sense (19's own
"find the first broken relation, not the whole failure tree"): "a
Command's own audit-trail row can be written before its target exists"
— true for every other Command in this codebase, false for
`CreateWorkspace`, because `commands.workspace_id`'s FK makes the
Workspace's own existence a precondition of recording the attempt
against it. This is not a defect in the schema or in the other
Commands; it is a genuine structural asymmetry the founding Command
alone exhibits, now disclosed rather than hidden (see Defect 3 above).

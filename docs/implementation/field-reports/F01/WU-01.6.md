## Implementation

### The one real fixture gap found: granting a HABB requires the holder to already be an ACTIVE Workspace member
This Work Unit's own test fixture (`_grant_directly`, granting a
non-`WORKSPACE_GOVERNANCE_RIGHT` binding directly, since no real
Command grants one yet) initially inserted a `human_authority_bindings`
row for a user who was never added as a Workspace member. A REAL,
pre-existing DB trigger (`trg_habb_check_grant_preconditions`, 05
GOV-005, migration `01a37c093cd6`) rejected it: `"target user %s has
no ACTIVE workspace_membership in workspace %s"`. This is not a defect
this Work Unit introduced — it is a real, correct precondition that
was simply never exercised by any earlier test (no earlier Work Unit
ever granted a non-founder HABB at all). **Fix, in the test fixture
only**: `_grant_directly` now calls the real `add_member` Command
first (never a direct insert into `workspace_memberships`) before
inserting the binding row directly. A second, related trigger
(`trg_habb_check_immutable`, same migration) additionally rejected a
directly-inserted `state=REVOKED` fixture row missing
`revoked_by_user_id`/`revoked_at` — a real `ck_habb_revoked_consistency`
CHECK constraint, fixed the same way (fixture now sets both together
when constructing an already-revoked row).

### `trg_habb_check_immutable` is a real, independent second line of defense for "REVOKED is terminal"
Discovered while designing `revoke()`'s own guarded `UPDATE`: the same
migration that added the grant-precondition trigger also added
`trg_habb_check_immutable`, which independently rejects ANY further
`UPDATE` once `OLD.state = 'REVOKED'`, and separately rejects any
`UPDATE` that changes `human_user_id`/`authority_class`/`scope_type`/
`scope_id`/`authority_source`/`granted_by_user_id`/`granted_at`.
`revoke()`'s own `UPDATE` only ever touches `state`/`revoked_by_user_id`/
`revoked_at`/`record_version` — confirmed compatible, and this
Work Unit's own application-level guard (`WHERE state = ACTIVE`,
`AuthorityBindingConflict` on 0 rows) and this DB-level trigger now
independently enforce the identical "REVOKED is terminal" rule, the
same "checked at two independent layers" discipline WU-01.5 already
established for membership uniqueness.

### Design decisions, each grounded in already-closed architecture or an established Work-Unit precedent
- **`GovernanceRootOrphaningRefused`, raised before any boundary
  evaluation, if `binding_id` names the Workspace's own currently-
  ACTIVE `WORKSPACE_GOVERNANCE_RIGHT` binding**: exactly one such
  binding exists per Workspace (`CreateWorkspace`'s own founder self-
  grant; `AddMember` already refuses to grant a second one). Revoking
  it would leave the Workspace permanently un-administrable — every
  governance operation's own BND-005 gate requires a currently-ACTIVE
  `WORKSPACE_GOVERNANCE_RIGHT` binding to ever reach ALLOW. This is
  05's own `GAP-05-001` ("Workspace Root Creation and Succession...
  owner transfer and succession remain undefined"), `[UNDERDEFINED]` —
  refused outright, the identical "STOP rather than invent" discipline
  `OwnerRoleNotAssignable` already established in WU-01.5, not a new
  HARD-DEP or bootstrap decision of this Work Unit's own making.
- **BND-004 `accepted_roles={Owner}` / BND-005
  `required_authority_class=WORKSPACE_GOVERNANCE_RIGHT,
  scope_type="WORKSPACE"`**: identical gate to `AddMember`'s own — only
  the Workspace's own governance root may administer authority
  bindings (05's closure: "Workspace governance root administers
  membership and role assignments"), re-checked fresh by
  `AuthorityResolver` on every call.
- **`AuthorityBindingNotFound`, a distinct exception from
  `RevokeAuthorityBindingDenied`**: the actor-side boundary chain only
  proves facts about the actor and the Workspace — it can legitimately
  ALLOW even when the supplied `binding_id` does not exist, or belongs
  to a different Workspace than claimed. Unlike `RecordHumanDecision`
  (whose BND-007 naturally fails closed when the Decision is missing,
  because that boundary input is then simply never set), no
  state-transition evaluator exists yet for a HABB's own lifecycle —
  so this Work Unit checks binding existence/ownership explicitly,
  immediately after the chain ALLOWs, before any commit is attempted.
  Disclosed as a deliberate, narrower mechanism than the Decision
  domain's own, not a shortcut.
- **`workspace_id` non-existence denied *before* `record_attempt`**:
  identical fix to the one WU-01.5 applied locally to `add_member` for
  the same `commands.workspace_id` FK hazard — mirrored here rather
  than reintroduced.
- **`revoke()` mirrors `DecisionRepository.record_decision`'s shape
  (guarded `UPDATE`, `AuthorityBindingConflict` on 0 rows), not
  `grant()`'s shape (plain insert)**: revoking mutates an EXISTING row;
  granting creates a new one. The version-guarded `UPDATE` also
  doubles as the "already REVOKED" guard by construction (no separate
  exception type needed — an already-`REVOKED` row simply never
  matches `WHERE state = ACTIVE`).
- **No HTTP route** — `AddMember`'s own disclosed scope boundary
  ("WU-01.8's own scope") applies identically here; not this Work
  Unit's concern.
- **The Membership-role "revoke role" operation (GAP-04-014's own
  remaining item) is NOT this file** — this Work Unit revokes a
  *HumanAuthorityBinding* (04 §6), a structurally different row/
  lifecycle from a Membership *role assignment* (05 §5); the latter
  remains `SUCCESSOR_NOT_BUILT`, matching WU-01.5's own disclosed
  boundary.

## Negative / adversarial tests
- Revoking the Workspace's own `WORKSPACE_GOVERNANCE_RIGHT` binding:
  `GovernanceRootOrphaningRefused`, zero rows changed, exactly 1
  `commands` row for the whole Workspace (`CreateWorkspace`'s own —
  proves no attempt was even recorded for the refused revoke).
- A `Contributor` member attempting to revoke another user's binding:
  denied (BND-004), binding stays ACTIVE.
- An actor with no membership at all in the target Workspace: denied
  (BND-003), binding stays ACTIVE.
- Non-human actor (`SYSTEM_SERVICE`/`AI_PROCESSOR`/`EXTERNAL_SYSTEM`,
  parametrized): denied (BND-001), binding stays ACTIVE.
- A genuinely non-existent Workspace: denied (BND-002, via the
  pre-check mirroring `AddMember`'s own fix).
- A genuinely non-existent `binding_id`: `AuthorityBindingNotFound`.
- A real `binding_id` that belongs to a DIFFERENT Workspace than
  claimed: `AuthorityBindingNotFound`, not silently revoked under the
  wrong Workspace's authority — binding stays ACTIVE, proves BND-002's
  own claimed-ID non-collapse extends to this Command's own extra
  object reference.
- Revoking an already-REVOKED binding (revoked by this Command,
  in-process): `CommitFailedPrecommit` (real `StaleVersionConflict`
  from the guarded `UPDATE`).
- Revoking a binding that was ALREADY `REVOKED` before this Command
  ever touched it (a pre-revoked fixture row, never revoked by this
  process): `CommitFailedPrecommit`, identical path — proves the guard
  is the real stored `state`, not merely in-process bookkeeping.
- Cross-Work-Unit proof: revoking a binding removes it from
  `AuthorityBindingRepository.list_current_bindings` for its holder —
  the vertical actually composes, not just each piece in isolation.

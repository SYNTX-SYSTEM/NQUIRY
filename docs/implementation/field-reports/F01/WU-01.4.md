## Options, as I understand them from the actual architecture — not a recommendation, a menu

**Option A — Self-service founder.** Any human who has completed a
real, verified login (now real, since the local-login-auth field) may
create a new Workspace; the creator's own `HumanAuthorityBinding`
(`WORKSPACE_GOVERNANCE_RIGHT`) is granted at creation time, through a
real governed Command with a real audit trail — mechanically identical
to what `NonProofWorkspaceBootstrap` already does as a fixture, just
promoted to a real, non-fixture, `CommitCoordinator`-backed path.
Legitimacy source: "a verified human, by the act of creating a
Workspace, becomes its own first governance root" — the same model
almost every comparable product uses (a new Slack workspace, a new
GitHub organization, a new Notion workspace). Requires exactly one
product decision: is verified-identity-plus-creation-act sufficient,
with no further external approval step? Cheapest to build — invents no
new authority concept; 04's existing `AuthorityClass`/`ActorClass`
vocabulary already covers it entirely.

**Option B — External/operator-granted root.** A designated authority
outside the normal per-Workspace governance model (e.g. an
allowlist, invitation code, or a "platform operator" role) explicitly
grants the first Workspace's governance right to a specific verified
human. This is NOT free — `04_AUTHORITY_AND_DECISION_RIGHTS.md`'s own
closed `ActorClass`/`AuthorityClass` vocabularies have no
"platform operator" concept today; adding one would itself be new
architecture, not an implementation detail, and is exactly the kind of
semantic invention this Field-execution process (and every predecessor
package) has consistently refused to do without an explicit human
decision.

**Option C — Defer, stay fixture-only for this execution cycle.**
Explicitly decide NOT to close HARD-DEP-001 during F01 (or F00-F12 at
all). `NonProofWorkspaceBootstrap` remains the only Workspace-creation
path, permanently disclosed as `NON_PROOF_FIXTURE`. F01 passes
"mechanically under fixture lane only with fixture ceiling" — its own
literal PASS definition already permits this outcome; nothing about
this Field requires HARD-DEP-001 to close.

I lean toward Option A as the cheapest and most product-realistic if a
decision is wanted now (it requires no new architecture, only a
product-legitimacy judgment call that is explicitly yours to make —
not mine), with Option C as the safe default if you'd rather keep this
open and bounded for now. Option B is real but meaningfully larger
scope (new authority concept) and I would not build it without a
separate, dedicated architecture pass.

## HUMAN DECISION (recorded 2026-09-21)

**HARD-DEP-001 RESOLVED — Option A: self-service founder.**

Decision, verbatim from the human operator: "Any real, verified human
(i.e. authenticated through the real local-login system, not a
fixture/mock identity) may create a Workspace and becomes its
governance root at that moment of creation, via a real governed
Command (not a raw DB insert, not first-login-implies-owner as a side
effect -- an explicit 'create Workspace' action that establishes root
authority as its own legitimate consequence)."

**Explicit scope constraint, binding on the implementation**: this
authorizes UNGATED self-service creation for now — no invite-only
gate, no admin-approval step, no allowlist — but the implementation
must NOT foreclose adding an approval/invitation gate later. The
eligibility check must be a named, replaceable step, even though today
it always returns eligible — never hardcoded so deep that a future
gate would require re-architecting the Command.

This closes HARD-DEP-001 for the prototype's own scope (a real,
governed, audited path now exists) — it does not retroactively
reclassify any EARLIER fixture-rooted Workspace (the local-login-auth
field's own demo Workspace, and every PKG-era test fixture) as
legitimate; those remain `NON_PROOF_FIXTURE`, unchanged, by
construction (see `CreateWorkspace`'s own implementation below for why

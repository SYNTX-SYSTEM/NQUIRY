## Additional finding, investigated and fixed: stale baked-in default Workspace/Session IDs
After the reseed, a real, unmocked browser check (same technique
WU-01.8/01.9 already used) surfaced a genuine, visible regression from
the reset itself: `docker-compose.yml`'s own
`NEXT_PUBLIC_DEFAULT_WORKSPACE_ID`/`NEXT_PUBLIC_DEFAULT_SESSION_ID`
defaults are hardcoded to the PRE-reset demo's own IDs
(`01a0c312-...`) — a fresh seed always generates new UUIDv7 IDs, so
the running `web` container's own baked-in default (read at `next dev`
process start, per that env var's own established behavior) pointed
at a Session that no longer exists:
```
$ curl .../workspaces/01a0c312-.../sessions/01a0c312-... -b <real session cookie>
{"kind":"denied","result":"DENY","reasonCode":"SESSION_NOT_FOUND"}
```
This would have left the app's own root-route redirect landing on a
real, but confusing, `SESSION_NOT_FOUND` denial screen for any human
opening `http://localhost:3000/` right now — not the intended,
inspectable demo state this Field's own prior reports have always left
running. **Fixed**: added `NEXT_PUBLIC_DEFAULT_WORKSPACE_ID`/
`NEXT_PUBLIC_DEFAULT_SESSION_ID` (the new, real IDs) to the repo's own
gitignored, local-only `.env` file, then recreated the `web` container
(`docker compose -p nquiry --profile app up -d --build web`) so it
picks up the corrected values. Re-verified with a real, unmocked
Playwright script:
```
login (demo-owner@nonproof.test) -> real redirect ->
http://localhost:3000/workspaces/01a0c5ee-.../sessions/01a0c5ee-...
[data-testid="session-view-ok"] visible, real Challenge text present
CONSOLE_ERRORS: []
```
Playwright suite (37 tests) re-run after this `web` container
recreation to confirm no regression from the rebuild itself — still
37 passed.

## 23.3 Required steps (each executed and recorded; none skipped silently)

1. **FALSIFIER RED.** A failing proof exists before the repair, and it fails for the right reason.
2. **FIRST BROKEN RELATION.** Trace `VISIBLE EFFECT → CONSUMER → RELATION → PRODUCER → AUTHORITY → STATE → FIRST BROKEN RELATION`.
3. **AUTHORITATIVE HOME.** Name the architecture home of the broken relation.
4. **MINIMUM LEGITIMATE ROOT REPAIR.** Repair at the home, not where the error is merely visible.
5. **PROPAGATION.** Inspect at minimum every applicable direct consumer, indirect consumer, sibling, parent Field, child Field, persistence, API, frontend projection, test, report, runtime evidence and downstream Field. Record each as affected or not affected, with the reason.
6. **LOCAL PROOF.**
7. **INTEGRATION PROOF.** Isolated unit tests do not substitute for integration proof. Where the Work Unit crosses domain, persistence, state, authority, application, API or projection boundaries, prove the complete relation across those boundaries.
8. **PRESERVATION PROOF.** Before the Delta, explicitly bind CURRENT STATE, BASELINE EVIDENCE, MUST BECOME TRUE, MUST REMAIN TRUE, MUST REMAIN IMPOSSIBLE, RECOVERABLE PREDECESSOR STATE, STATE ISOLATION, FALSIFIERS and AUTHORIZED DELTA. After the Delta, prove that every MUST REMAIN TRUE still holds.
9. **REGRESSION PROOF.** Run the relevant existing predecessor and cross-field tests. A new capability may not silently break an accepted predecessor Field.
10. **INVERSE PROOF.** Trace the resulting visible or persisted effect back through `PROJECTION → API / CONSUMER → PERSISTENCE / APPLICATION → DOMAIN → EFFECT GATE → STATE → AUTHORITY → GOVERNANCE`. No inverse chain may end in an assumption.
11. **RECURSIVE DEEP SWEEP.** Inspect the resulting Field for semantic drift, authority leakage, hidden cross-field mutation, state inconsistency, projection inconsistency, preservation regression, documentation drift and evidence drift.
12. **INVERSE DEEP SWEEP.** Start from the resulting effect and reconstruct back to its authoritative source.
13. **DOCUMENTATION / EVIDENCE.** Update or create the Field evidence. The record makes reconstructable what changed, why it changed, which relation was repaired, where the Authoritative Home is, which Authority authorized the Delta, what had to remain true, which proofs were run, which evidence was produced, what remains open, what the resulting Field status is, and which predecessor can be restored.
14. **FIELD RECONSTRUCTION.** After every material Delta: `DELTA → RE-READ → COMPARE EXPECTED STATE → RECONSTRUCT FIELD → DETERMINE RESULTING FIELD STATUS`.
15. **HUMAN REVIEW WHERE REQUIRED.** Where the Field requires human review, especially for a material CYAN frontend change, technical proof alone is insufficient.
16. **CHECKPOINTING.** A materially accepted Field is not used as the predecessor for the next material Delta until the required recoverable predecessor and checkpoint conditions (§11) are satisfied.
17. **RESULTING FIELD STATUS.** Use the Operating Manual status vocabulary only. Never claim FIELD_GREEN, REVIEWED_FIELD, PUBLISHED_FIELD or COMPLETE before the corresponding conditions exist (§18).

## 23.7 Non-code Work Units

A Work Unit whose Delta is a Git publication or checkpoint act (for example WU-PFC-00: commit, push, tag and verify an accepted predecessor) is executed only under explicit publication authority (§11, §19). It uses the §23.4 header and the §23.6 completion report. Its proof steps are the checkpoint verification of §11 (remote commit and tag target), followed by field reconstruction. Steps 1–12 of §23.3 apply only where such a Work Unit also changes material code, schema, API or projection.

## 23.8 Precedence

§23 is additive. Where it and an earlier section both apply, both hold. §23 does not authorize any Work Unit by itself: implementation still begins only under §11 and §21.
